# Comments & Docblocks

A comment is read by someone who has the code in front of them. It earns its place by saying something the code cannot.

---

## 1. A comment stands on its own

Whoever opens the file has the code and nothing else. A comment that sends them somewhere they cannot go says nothing.

Do not point at anything outside the repository: planning documents, specs, ticket numbers, review notes, or task tracking identifiers.

```ts
// Bad
/** Resolves the server id for a queued row (see the sync register, row 14). */

// Good
/** Resolves the server id for a queued row. */
```

A test name says what breaks, not where the requirement is filed.

```ts
// Bad
it('case 35 / AC-2: rejects a push whose clock is behind the last ack', ...)

// Good
it('rejects a push whose clock is behind the last ack', ...)
```

---

## 2. Describe the code, not the defect that led to it

The history of a bug belongs in the commit message, where it is attached to the change that fixed it. A docblock that narrates a past incident goes stale on the next refactor and buries the one sentence a reader needed.

```ts
// Bad
/**
 * Without this field the answer named the id that was sent: the second device
 * kept a local row the server had never heard of, so the next pull re-created
 * it, and the duplicate only surfaced after the third sync...
 */

// Good
/** Server-assigned id, echoed back so the client can replace its local one. */
```

"Why it is this way" is welcome when the reason is not obvious from the code. "What went wrong in July" is not.

---

## 3. Size is proportional to what is being explained

| What it explains | What it gets |
| --- | --- |
| One field, one flag, one constant | One line, maybe two |
| A non-obvious decision or trade-off | Two or three lines |
| A non-trivial algorithm or invariant | One paragraph |
| More than that | It is documentation — put it in `docs/` and link it |

Twenty lines of docblock on one optional field is not thoroughness, it is a document filed in the wrong place.

```ts
// Bad: twenty lines above one field
/**
 * The identifier the server assigned to this row.
 * ... fourteen more lines of background ...
 */
serverDocId?: string

// Good
/** Set once the server has accepted the row; absent while it is still queued. */
serverDocId?: string
```

---

## 4. What to write instead

Comments answer **why this and not the obvious alternative**, where the answer is not visible in the code:

- a constraint imposed from outside (a protocol, a driver quirk, an OS limit);
- an invariant the reader must preserve when editing;
- a trade-off that was deliberately taken.

What the code *does* is the job of the code and its names. If a comment is needed to explain what a function does, rename the function: a name is read at every call, a docblock only where it is written.

A function is named with an imperative verb phrase, because a name says what calling it does; a noun or a participle names the answer instead of the act.

```ts
// Bad
// Increment the counter by one.
counter += 1

// Bad
// Loop over users and check permissions.
for (const user of users) { ... }

// Good
// SQLite limits bound parameters to 999; chunk batches to stay safely below.
```

---

## 5. A type is commented all the way, or not at all

A field that carries a docblock among five that do not reads as five that were forgotten. Either every field earns its line, or what is worth saying about the type goes into the type's own docblock.

```ts
// Bad
export interface MediaRecord {
  id: MediaId
  kind: MediaKind
  /** What a block stores: a path the server will serve, never a blob url. */
  url: string
  name: string
}

// Good
/**
 * A stored file, as the library lists it and a block refers to it.
 *
 * `url` is what a block stores: a path the server will serve, never a blob url.
 */
export interface MediaRecord {
  id: MediaId
  kind: MediaKind
  url: string
  name: string
}
```

---

## 6. No trace of who wrote it

Code carries no sign of the agent, model, tool, or session that produced it. No `// added by agent`, no `// Claude:`, no `generated by`, no ticket/spec tag prefixes (`AC-1`, `(D-1)`). A file reads as if one person wrote it.

```ts
// Bad
// Implemented by the agent for AC-1.
export function applyPush(...)

// Good
export function applyPush(...)
```

Git carries no sign of it either. A commit message ends with its last paragraph: no `Co-Authored-By:` naming a model, no "Generated with" footer. A pull request body is the same — what changed and why, and nothing about what produced it.

---

## Checklist before handing a diff over

- [ ] No `(D-n)`, `(I-n)`, `(AC-n)`, `(T-*-n)` or similar tags anywhere, tests included.
- [ ] No comment narrating a past bug, a review round, or who asked for what.
- [ ] Every docblock is proportional to what it documents.
- [ ] Every remaining comment says *why*, not *what*.
- [ ] Every function is named with an imperative verb phrase.
- [ ] No type carries a comment on some of its fields and not the rest.
- [ ] Everything is in English: code, comments, test names, sample content.
- [ ] Nothing in the code or commit messages names an agent, a model, a tool, or a session.
