# ADR-0013: Vault identity, the service folder, and application state

- **Status:** Accepted
- **Date:** 2026-08-15
- **Related:** ADR-0000, ADR-0001, ADR-0002

## Context

ADR-0002 puts every vault's cache in one database, with a `vault_id` on every
row. Nothing so far says where that identifier comes from. ADR-0000 established
that the list of vaults is application state living outside every vault, and left
the location open; ADR-0002 said the index holds a `vaults` table that is a cache
of a registry it does not own.

Those two gaps meet in the first line of the first tool: it cannot write a row
until it knows what identifies the vault it is reading.

Path cannot be the answer. ADR-0001 accepts that folders are moved and renamed
outside the application, and identifying a vault by where it currently sits means
losing every row that referred to it the moment the user drags it somewhere else.

## Decision

### A vault carries its own identity, inside itself

```
<vault>/.numen/config.json
```

```json
{ "v": 1, "id": "01J8F3K2M9QRSTVWXYZ012" }
```

The identifier is a ULID, generated once, when the user **adds the vault to the
application**. It is never generated by scanning a folder: adding a vault is a
deliberate act by the user, and it is the moment the application is allowed to
write into that folder for the first time.

This is the identity `vault_id` refers to throughout the index.

### One service folder, named after the application

Everything the application writes into a vault that is not a note goes into that
one folder, in subfolders. Its name is a setting; the default is `.numen`.

Named after the application rather than after what it holds, because that is what
is true: the folder belongs to this application, and saying so makes it
impossible to collide with another tool that has the same idea. A vault opened by
both this application and Obsidian ends up with `.numen` next to `.obsidian`, and
neither has a claim on the other. A generic name would assert a shared standard
that does not exist.

The name remains configurable because a leading dot is not free — some sync tools
and file pickers skip hidden directories — and because there is exactly one such
folder, changing it is a setting rather than a restructuring.

The service folder is excluded from indexing in full.

### Application state lives with the application

The registry of vaults — which ones exist, where they are, which was open last —
and anything else about this installation lives in the platform's configuration
location (`~/.config/numen/` or the platform equivalent), as JSON.

JSON rather than a database, deliberately. It is a handful of entries, and the
one time it matters most is when the application will not start: a file a human
can open and fix beats a database that needs the application to read it.

### Consequences of losing either half

Losing the **registry** costs the user re-adding their vaults. No knowledge is
lost, because every vault still carries its own identity and every row in the
index still points at it.

Losing the **`.numen/config.json`** of a vault means the application no longer
recognises it: adding the folder again produces a new identity, and the old rows
in the index are orphaned. They are cache, so nothing irreplaceable dies, but the
work of rebuilding does. The file is small and worth backing up with the vault —
which happens by default, since it lives inside it.

## Consequences

**Positive**

- A vault survives being moved, renamed, or copied to another machine, and is
  recognised as the same vault when it arrives.
- The application writes into a vault exactly once without being asked to edit
  something, and that write is the direct result of the user adding the vault.
- Coexistence with other tools on the same folder is structural rather than
  hoped for.

**Negative**

- A folder appears inside the user's vault. It is one folder, it is named
  honestly, and it holds data that would otherwise have nowhere to live — but it
  is still ours in their space.
- **Copying a vault produces two vaults with the same identity.** Duplicating the
  folder duplicates `config.json`, and the application will see one vault in two
  places. This must be detected — same id, two paths — and put to the user, who
  is the only one who knows whether they meant a copy or a move. It cannot be
  resolved automatically: picking either answer silently is wrong half the time.

## Alternatives considered

**Identify a vault by its path.** Rejected: ADR-0001 accepts that folders move
outside the application, and this loses every row on the first move.

**Keep the identity only in the registry, write nothing into the vault.**
Rejected: the vault then means nothing on its own. Move it to another machine and
it is a new vault; two installations cannot agree that they are looking at the
same thing.

**Application state in SQLite.** Rejected: a database for ten rows, whose most
important moment is when the application is broken.

**A separate hidden folder per feature** (`.srs`, `.ocr`). Rejected: one folder
per vault, subfolders inside. The multiplication buys nothing and costs a
hidden-folder problem per feature.
