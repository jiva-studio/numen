# Architectural Layer & Boundary Validator (`@numen/lint-layers`)

Automated verification of architectural layer boundaries and invariants across
libraries, plugins, and desktop applications.

## Invariants Checked

Each check has an id, a scope (`libs`, `plugins` or `apps`) and a module; `node check.mjs --list` prints them. The checks that only run the ESLint or golangci-lint configuration of a package (`ui-components-lint`, `workbench-lint`, `plugin-loader-lint`, `desktop-editor-fsd`, `desktop-flashcards-fsd`, `mobile-fsd`, `plugin-frontend-slices`, `plugins-frontend`, `core-depguard`, `notes-depguard`, `sdk-isolation`) repeat the lint target of that package; `--without-lint` leaves them out. The checks that run Go tests (`go-structure`, `notes-hexagon`, `plugins-independence`) repeat tests that `go test ./...` of `libs/core/kernel` and `libs/note` runs; `--without-go-tests` leaves them out. `plugins-independence` is left out when `go-structure` runs, because that runs every test of `libs/core/kernel/container`.

1. **Libraries (`libs`)**:
   - `go-structure`: every test of `libs/core/kernel/container`, the package that contains the structural Go tests. They load the modules of `go.work` with go/packages, go/types, the AST and golang.org/x/mod/modfile: the layers of the core and the direction of its imports, the machine clock read only by a clock port implementation, no alias of another core package's type, the role of each adapter read from what it references and implements, no port reference from a driving adapter, the full method set of an interface within the interfacebloat maximum, no interface call inside a port, no package below the composition root, the plugin dependency rule over the type-checked import graph and over the direct requirements of each `plugins/*/go.mod`, and the plugin SDK encapsulating the whole `libs/core/protocol` module. It runs on any change to a Go file, a `go.mod` or `go.work`.
   - `library-matrix`: every `go.mod` under `libs/` belongs to a family, the first directory under `libs/`, and the family is a row of `LIBRARY_DEPENDENCIES` in `checks/libraries.mjs`. The `go.mod` and the Go files of a library, tests included, import only the modules of their own family, the families their row lists, and nothing outside `libs/`. A library with no row fails, so a new library declares its place before it is built. The rows are `core-client` to `protocol`; `plugin-sdk` to `protocol` and `ui` (its Vite helpers); `plugin-host` to `plugin-sdk` and `core-client`; `plugin-manager` to `ui`.
   - `protocol-declared-only-by-clients`: only `@numen/plugin-sdk` and `@numen/core-client` declare `@numen/protocol` in a `package.json` under `apps`, `libs`, `plugins` or `tools`; the imports are `dependency-graph`'s. It fails when it reads fewer than 15 packages or finds the two clients declaring the schema fewer than twice.
   - `core-client-private`: the package named `@numen/core-client` is `"private": true`, and it is not among the packages plugins rely on: the first-party packages a `package.json` under `plugins/` declares, and those they bring in through their `dependencies`, `peerDependencies` and `optionalDependencies`. It fails when that set is empty or it reads fewer than 15 packages.
   - `package-matrix`: every `package.json` under `libs/` is a row of `PACKAGE_DEPENDENCIES` in `checks/libraries.mjs`, keyed by package name, and declares only the first-party `@numen/*` packages its row lists. A library with no row fails, so a new library declares its place before it is built. `dependency-graph` restricts the imports of each library to the same row.
   - `core-depguard`, `notes-depguard`, `sdk-isolation`: `golangci-lint` with the depguard rules of `libs/core/kernel`, `libs/note` and `libs/plugin/sdk-go`.
   - `dependency-graph`: dependency-cruiser (`dependency-cruiser.mjs`, rules built in `checks/dependencies.mjs` from the packages under `libs`, `apps` and `plugins`) over the `src` of every library and application and the `frontend` of every plugin, type imports included. A plugin imports only `@numen/plugin-sdk` and `@numen/ui` of the first-party packages and nothing of `@connectrpc`; an application imports every library except `@numen/plugin-sdk` and `@numen/protocol`; a library imports only the row of the package matrix; no package imports a file outside its directory by a relative path; the plugin host imports only Vue and Vite of third-party code; a `lib`, `api` or `model` segment imports no higher segment of its slice outside tests and stories; nothing imports through `@x`; and no files form a cycle of runtime imports. A package whose `tsconfig.json` declares `paths` is checked alone with it, so its aliases resolve. It fails when it reads fewer than 1000 modules.
   - `styles-use-tokens`: stylelint (`stylelint.config.mjs` at the root, rules of its own in `stylelint-plugin.mjs`) over every tracked `.css` file and the `<style>` blocks of every `.vue` file: no hex colour, named colour or colour function outside a token file (a `tokens` directory) and a theme file (a `theme` or `themes` directory); no `--numen-` declaration outside those; no `var()` with a fallback; and no `var(--numen-…)` that no token file declares, the declared set read from the syntax trees of the token files; and, in `libs/ui`, `libs/plugin/manager`, `apps/desktop` and `plugins/*/frontend`, no length on a property (`numen/no-bare-length`): a size is a `var()` of a local custom property in `rem` or `em`, `px` appears only as a 1px border width, zero, percentages and viewport units pass, and token and theme files are exempt. A self-test lints a planted component that must fail. It fails when it reads fewer than 150 files.
   - `ui-components-lint`: `npm run lint` passes in `libs/ui/components`.
   - `workbench-lint`: `npm run lint` passes in `libs/ui/workbench`.
   - `plugin-loader-lint`: `npm run lint` passes in `libs/plugin/loader`.
   - `notes-hexagon`: every test of the root package of `libs/note` (`layers_test.go`, `purity_test.go`).
   - `notes-depguard`: Notes Library Depguard Boundaries.
   - `sdk-isolation`: Plugin SDK Go Isolation (no core or app imports).
   - `sdk-ts-encapsulates-protocol`: `checks/sdkProtocol.mjs` builds a TypeScript program from every script entry of the `exports` of `libs/plugin/sdk-ts` (a condition object is read by its `types`, `import` or `default` target, a `*` pattern by the files it matches) and fails when the type of an exported declaration refers to a declaration located in `libs/core/protocol`: a re-export, a signature, a member, a type argument, a base type or a constraint, found through the type checker. It fails when it reads fewer than 2 entries, 100 exported declarations, 15 SDK source files or no file of the schema.
   - `all-ts-packages-eslint`: every directory under `libs` or `apps` that holds a `tsconfig.json` and a `package.json` has an `eslint.config.js`; it fails when it reads fewer than 8 packages.
   - `pure-segment-rule`: every package with a `lib` segment resolves `numen/pure-segment` as an error on a file of it (`eslint --print-config`). The rule (`numen-rules.mjs`, tested in `pureSegment.test.mjs` and, for a plugin, in `checks/pluginConfig.test.mjs`) fails, in a non-test file of a `lib` folder, an import of Vue, Pinia, `@vue/*` or a `.vue` file; a browser global (`window`, `document`, `navigator`, storage, `location`, timers, frames, microtasks, observers, `fetch`) also through `globalThis`; a DOM type (`HTMLElement`, `Element`, `Node`, `Range`, the event types, `DOMRect`) that no file declares or imports; a call that builds, queries or listens to the DOM (`createElement`, `addEventListener`, `querySelectorAll`, `dataset`); `Date.now()`, `new Date()` and `Math.random()`; and a platform port of `@numen/ui` (`doc`, `win`, `nav`, `getNow`, `browserClock`). It fails when it reads fewer than 19 packages.
   - `typecheck-covers-sources`: no `exclude` entry of a tracked `tsconfig*.json` names a tracked file, as a path, a folder or a glob, read from the JSON syntax tree of the configuration. Build output such as `dist` and `node_modules` is not tracked, so excluding it passes. It fails when it reads fewer than 20 configurations.
   - `no-component-below-ui`: over the modules dependency-cruiser reads (`readModuleGraph` in `checks/dependencies.mjs`), no `.vue` file of a library, a window or a plugin frontend has `lib`, `api` or `model` as its nearest segment folder. It fails when it reads fewer than 200 components.
   - `strict-lint-rules`: every directory with an `eslint.config.js` or `eslint.config.mjs`, and every directory with a `package.json` that no such directory contains (the root `package.json`, which declares the workspace, aside), resolves (`eslint --print-config` on a source file and a test file) `no-void`, `no-empty` (`allowEmptyCatch: false`) and the typed `@typescript-eslint` rules `no-empty-function`, `no-floating-promises` (`ignoreVoid: false`), `no-misused-promises`, `await-thenable` and `switch-exhaustiveness-check` as errors. A package of scripts only (`tools/eslint.config.mjs`) resolves the untyped three (`no-void`, `no-empty`, `no-empty-function`) on a source script and a test script, from `createStrictScriptRules`. The shared definition is `createStrictRules` in `base-eslint.mjs`; `plugins/.example/eslint.config.js` contains the same block because a plugin config imports nothing outside its directory.
   - `public-component-has-story`: for the entry `src/index.ts` of each package under `libs/ui`, `checks/stories.mjs` follows the export declarations through the TypeScript syntax tree (named re-exports, `export *`, an import that is exported again, a type export skipped) to the `.vue` files exported as default; each must be rendered by a `*.stories.ts` file of the same package, which means the story imports the component, directly or through a folder `index.ts`, and uses the imported name. It fails when it reads fewer than 20 components or 20 story files.
   - `emitting-component-has-play-story`: of those public components, each whose `<script>` calls `defineEmits` or `defineModel` (read from the script's syntax tree) must be rendered by a story file in which an exported story, or the default export, has a `play` member. It fails when it reads fewer than 10 such components.
   - `story-files-lint-storybook-recommended`: `eslint --print-config` on the first story file of `libs/ui/components` and `libs/ui/workbench` must resolve each rule of the installed plugin's `flat/recommended` config for story files at the plugin's severity, and `storybook/csf-component` off. The expected rules are read from the plugin, not listed. It fails when the plugin gives fewer than 5 rules.
2. **Plugins (`plugins`)**:
   - `plugins-independence`: the `Plugin` tests of `libs/core/kernel/container`.
   - `plugins-leakage`: every `manifest.json` has an id, a name and a version; there is no shared plugin folder; no plugin imports `libs/core/kernel`.
   - `plugins-hold-no-schema`: no tracked file under `plugins/(*)/` is a `.proto` schema; a plugin calls the core through the SDK.
   - `plugins-frontend`: ESLint over `plugins/` with each plugin's copy of the golden `eslint.config.js`: no `@/**` or `@plugins/**` import; a file of a `lib` segment imports no `ui`, `model` or `api` segment at any depth and no `.vue` file; every component passes `numen/max-inline-props`, `numen/vue-script-sections`, `numen/handler-naming` and `numen/max-script-lines`, and every source passes `max-lines` 350 and `complexity` 10; a test passes `numen/no-style-declaration-read` and `numen/no-mock-of-subject-slice`. The code of the rules is `plugins/.example/numen-rules.mjs`, a byte-identical copy of `tools/lint-layers/numen-rules.mjs` (a plugin configuration imports nothing outside its directory); `plugin-config-golden-parity` fails when the two differ. `checks/pluginConfig.test.mjs` lints planted files in a copy of the template.
   - `plugin-frontend-slices`: the shape of every plugin frontend and the rule that keeps its slices apart. A frontend holds `index.ts`, `words.ts`, `types.ts` and `styles.css` at its root, the shared `api` and `lib`, the composing `ui` and `model`, and slices; a slice holds its `index.ts` and the segments `ui`, `model`, `api` and `lib`, nothing else (tests, stories and `fixtures`, `testdata`, `testing` folders aside). The `boundaries/dependencies` rule of `plugins/.example/eslint.config.js` refuses an import of a slice except through its `index.ts`, an import of a sibling slice, and an import from a slice of the composing `ui` and `model`. The check fails when it reads fewer than 10 slices or 500 frontend files, and when a planted frontend of two slices in a copy of the template is not refused at the three imports that break the rule.
   - `plugin-config-golden-parity`: every plugin carries byte-identical copies of `plugins/.example/eslint.config.js`, `numen-rules.mjs`, `tsconfig.json` and `Makefile`, and of the root `.golangci.yml`.
   - `plugin-backend-layers`: Plugin Backend Internal Hexagonal Layer Direction.
   - `plugin-service-size`: the non-test code of a plugin's `backend/service` is at most 600 lines; the rule fails when it reads fewer than 15 services.
   - `plugins-use-main-entry`: a plugin names `@numen/plugin-sdk` and `@numen/ui` through the main entry. A deep path must be an entry the package declares in `exports`, and it passes only as the `testing` entry, as a stylesheet, or from a build configuration file (`*.config.ts`). The exports are read from the `package.json` of each package, and the rule fails when it reads fewer than 100 references.
3. **Applications (`apps`)**:
   - `core-client-only-in-api`: in every application that declares `@numen/core-client` and is cut into layers (an entry `src/main.ts` and an `app` layer), only the entry and the shipped files of an `api` segment import `@numen/core-client`, read from the resolved import graph.
   - `shared-serves-several-slices`: in the same applications, each shipped file of `src/shared` is used by more than one slice (`layer/slice` on `pages`, `features` and `entities`, the layer otherwise). Its users are the files outside `shared` that import it, and the users of the shared files that import it. It fails when it reads fewer than 5 shared files.
   - `app-is-composition`: in the same applications, no shipped source file of `src/app` is longer than 300 lines, no file there is named as a composable (`use<Name>`) and none exports one. It fails when it reads fewer than 10 files.
   - `app-binds-in-order`: in the same applications, no shipped source file of `src/app` (a component included) holds, by its syntax tree, a `{ current?: ... }` holder, a `.current = ...` assignment, an `Object.assign` onto an object made before, a `.provide(...)` call on a state, a `ref`, `shallowRef` or `reactive` that starts as `{}` or as a stub of empty functions, or an interface whose fields are all optional. A part that two others need is made first and handed to both; a mutual dependency goes through a port made first. It fails when it reads fewer than 36 files; `checks/frontendGraph.test.mjs` plants each form.
   - `pages-are-composed-not-consumed`: no shipped file of `entities`, `features` or `shared` imports a page, and a shipped file of `app` takes from a page only a `create<Name>Page`, and a component of `app` also the components it draws. It fails when it reads fewer than 280 files.
   - `testing-reaches-slices-by-index`: no file of `src/testing` imports or re-exports a path inside a slice; it takes a slice through its index. It fails when it reads fewer than 10 files.
   - `desktop-editor-fsd`, `desktop-flashcards-fsd`, `mobile-fsd`: the Feature-Sliced Design layer hierarchy (`shared` → `entities` → `features` → `pages` → `app`), by `npm run lint` in each window.
   - `desktop-flashcards-fsd`: Desktop Flashcards FSD Layer Hierarchy.
   - `mobile-fsd`: Mobile FSD Layer Hierarchy.

## Structural checks

Every check below derives its subject from the repository (the manifests, `go.work`, the directories) and names no plugin, package or file. Each declares a minimum count of what it examines, so a rule over nothing fails.

- `plugins-isolation-capture`: one rule over the capture `plugins/(*)/`: a Go import or a package dependency of plugin X names plugin Y only when X equals Y. The imports of scripts are `dependency-graph`'s, and the Go import graph is checked by `libs/core/kernel/container/plugin_isolation_packages_test.go`, over the type-checked packages of every plugin module.
- `no-suppressions`: no `nolint`, `eslint-disable`, `eslint-enable`, `@ts-expect-error`, `@ts-ignore` or `@ts-nocheck` comment; no `exclusions`, `exclude-functions`, `exclude-rules`, `exclude-dirs`, `exclude-files` key in a golangci configuration; no source file named in an eslint `ignores` or `files` entry; no array of repository files, in a constant or inline, in a script of `tools/lint-layers` or `stylelint.config.mjs`. Generated code is detected by its `Code generated ... DO NOT EDIT` header and is not read. It reads comments with `typescript` and `@vue/compiler-sfc`, which `package.json` declares.
- `every-path-has-a-layer`: every Go module and npm package is under `libs`, `plugins`, `apps` or an auxiliary root (`tools`, `tests`, `docs`); no file is directly in a layer root; every plugin directory has a `manifest.json`.
- `workspace-lists-every-module`: `go.work` uses exactly the directories that hold a `go.mod`.
- `json-keys-camelcase`: every JSON key in a plugin manifest (including JSON schemas), API fixture and TypeScript JSON type is `camelCase`.
- Before a verifier that runs `golangci-lint` starts, the linter must be built with a Go no older than the `go` line of `go.work`.

The checks are tested with violation fixtures: `npm test` in this directory.

## Usage

```bash
# Via Makefile:
make check_layers                     # all layers across monorepo
make check_layers target=libs         # library layers only
make check_layers target=plugins      # plugins isolation and boundaries
make check_layers target=apps         # application FSD layers
make check_layers target=core         # specific module
make check_dependencies               # dependency-cruiser alone (dependency-graph)
make check_styles                     # stylelint alone (styles-use-tokens)

# Directly:
node check.mjs [target...]
node check.mjs --list
node check.mjs --help
```
