# Checks (`@numen/checks`)

The structural, style and documentation checks of the repository, in one place, with a registry that selects and runs them. Each check has its own folder with its code, its planted-violation test and its fixtures. Rules stay in the tool that applies them: the ESLint configuration and rule files and the stylelint plugin are in `tools/lint-layers`, the golangci-lint configurations are at the root, and the registry lists them with the runner `eslint` or `stylelint` (the runner runs the tests that prove the rules; each package applies them in its own lint target). Dead code (knip) is a separate tool in `tools/lint-quality`.

## Layout

```
tools/checks/
  rules.json            the registry: the tag vocabulary and one entry per check
  run.mjs               selects the checks, runs them, prints one report and one exit code
  registry.test.mjs     the rules the registry itself must keep
  lib/                  changed.mjs (files a branch changes, path patterns), report.mjs, plant.mjs (a tree reduced
                        to some paths), graph.mjs (the repository, the Go and TypeScript readers), golangci.mjs
  structure/go/         one Go module in go.work: load/ (the type-checked workspace, findings, the layout of the
                        kernel) and one folder per check with check.go, check_test.go
  structure/ts/<name>/  check.mjs (the verifiers), check.test.mjs (planted violations)
  style/comments/       comments the name and type already state (Go command and TypeScript reader)
  style/names/          narrative identifiers, test names, comments, documents and strings
  docs/paths-exist/     backticked paths in the architecture documents name files that exist
```

The Go check `spelling` is a style check; it is in `structure/go/spelling` because it shares `load/`. A Go check runs from the container of the kernel (`libs/core/kernel/container`), where the checks lived before: importing `load` changes the working directory to it, and the relative paths of the checks are written against it.

## The registry

An entry of `rules.json` has a `name`, the `paths` it reads (patterns with `**`, `*`, `?` and `{a,b}`), its `tags`, the `selftest` (the file with its planted violations, relative to this folder) and a `runner`: `go` (a package of `structure/go`), `verifiers` (the exported verifiers of a module run in process), `command`, `eslint` and `stylelint` (the tests that prove the rule files run). `go` marks a check that runs as a Go test and `ts` one that runs as a Node script, whatever language it reads. `node run.mjs --tags ?` prints the tags with their meaning.

`registry.test.mjs` fails on a tag outside the vocabulary, a check with neither `fast` nor `slow` (or both), a missing selftest, a check folder that is not listed, a path pattern that matches no tracked file, and a `verifiers` check that gives another answer on a tree reduced to its `paths` (the check reads a file outside them). The reduced tree is not tried for the `go` checks (they type-check the workspace with `go list`, which needs `go.work` and every module), nor for commands and rule tests.

## Selection

```bash
make checks                          # every check
make checks TAGS=fast,ts             # all of the tags (and)
make checks TAGS='go|ts'             # one of the groups (or); a group is tags joined by commas
make checks TAGS=?                   # the tags
make checks EXCLUDE=slow             # without the checks that carry the tag
make checks ONLY=go/layers,ts/styles # the named checks
make checks CHANGED=1                # the checks whose paths a change of the branch touches
make checks LIST=1                   # what runs and why; nothing runs
make checks_selftest                 # the planted-violation tests (takes the same selection)
```

`CHANGED=1` reads the diff against `origin/main` (`BASE_REF` names another base), the uncommitted changes and the untracked files. A check runs when a changed file matches its `paths`, lies in its own folder or in `lib/`; a change of `run.mjs`, `rules.json` or `lib/` selects every check. The checks tagged `gate` have wide paths and run whenever anything in their area changes. `make lint_layers` (`check_layers`) is `TAGS=structure`, `lint_comments` is `ONLY=style/comments` and `lint_narrative` is `ONLY=style/names`, each with its planted-violation tests first.

CI runs everything: the Architecture job runs `make checks EXCLUDE=go` and the tests of this folder, and the job Structure Checks of `go.yml` runs `make checks TAGS=go`.

## Invariants Checked

Each verifier has an id, a scope (`libs`, `plugins` or `apps`) and a module. A verifier module is one check folder of the registry; `make checks LIST=1` prints the folders. The checks that only run the ESLint configuration of a package (`plugin-frontend-slices`, `plugins-frontend`) repeat the lint target of that package; `--without-lint` leaves them out. A check does not repeat what a package's own lint target or `go test` runs in CI: the depguard rules, the lint of the libraries and windows are those targets'.

1. **Libraries (`libs`)**:
   - `library-matrix`: every `go.mod` under `libs/` belongs to a family, and the family is a row of `go` in `library-matrix.json` (beside `structure/ts/libraries/check.mjs`). The family of a library is its path under `libs/` up to the outermost directory that holds a `go.mod` and contains it, so `libs/plugin/sdk-go/host` is of the family `plugin/sdk-go` and `libs/note` of `note`; no list of nested folders is kept. The `go.mod` and the Go files of a library, tests included, import only the modules of their own family, the families their row lists, and nothing outside `libs/`. A library with no row fails, so a new library declares its place before it is built.
   - `protocol-declared-only-by-clients`: only `@numen/plugin-sdk` and `@numen/core-client` declare `@numen/protocol` in a `package.json` under `apps`, `libs`, `plugins` or `tools`; the imports are `dependency-graph`'s. It fails when its selector matches nothing.
   - `core-client-private`: the package named `@numen/core-client` is `"private": true`, and it is not among the packages plugins rely on: the first-party packages a `package.json` under `plugins/` declares, and those they bring in through their `dependencies`, `peerDependencies` and `optionalDependencies`. It fails when that set is empty or it reads no package.
   - `package-matrix`: every `package.json` under `libs/` is a row of `packages` in `library-matrix.json` (beside `structure/ts/libraries/check.mjs`), keyed by package name, and declares only the first-party `@numen/*` packages its row lists. A library with no row fails, so a new library declares its place before it is built. `dependency-graph` restricts the imports of each library to the same row: `libraries.mjs` and `dependency-cruiser.mjs` read the one file `library-matrix.json` (beside `structure/ts/libraries/check.mjs`). The rows are `core-client` to `protocol`; `plugin-sdk` to `protocol` and `ui` (its Vite helpers); `plugin-loader` to `plugin-sdk` and `core-client`; `plugin-manager` to `ui`.
   - `dependency-graph`: dependency-cruiser (`dependency-cruiser.mjs`, rules built in `structure/ts/dependency-graph/check.mjs` from the packages under `libs`, `apps` and `plugins`) over the `src` of every library and application and the `frontend` of every plugin, type imports included. A plugin imports only `@numen/plugin-sdk` and `@numen/ui` of the first-party packages and nothing of `@connectrpc`; an application imports every library except `@numen/plugin-sdk` and `@numen/protocol`; a library imports only the row of the package matrix; no package imports a file outside its directory by a relative path; the plugin host imports only Vue and Vite of third-party code; a `lib`, `api` or `model` segment imports no higher segment of its slice outside tests and stories; nothing imports through `@x`; and no files form a cycle of runtime imports. A package whose `tsconfig.json` declares `paths` is checked alone with it, so its aliases resolve. It fails when its selector matches nothing.
   - `styles-use-tokens`: stylelint (`stylelint.config.mjs` at the root, rules of its own in `stylelint-plugin.mjs`) over every tracked `.css` file and the `<style>` blocks of every `.vue` file: no hex color, named color or color function outside a token file (a `tokens` directory) and a theme file (a `theme` or `themes` directory); no `--numen-` declaration outside those; no `var()` with a fallback; and no `var(--numen-…)` that no token file declares, the declared set read from the syntax trees of the token files; and, in `libs/ui`, `libs/plugin/manager`, `apps/desktop` and `plugins/*/frontend`, lengths (`numen/no-bare-length`): a `rem` or `em` literal may stand on a property, `px` appears only as a 1px border width, a `rem` or `em` literal may also stand in any custom property (`--max-width: 40rem`), any other unit fails (px in a custom property too), zero, percentages and viewport units pass, and token and theme files are exempt. A self-test lints a planted component that must fail. It fails when its selector matches nothing.
   - `sdk-ts-encapsulates-protocol`: `structure/ts/sdk-protocol/check.mjs` builds a TypeScript program from every script entry of the `exports` of `libs/plugin/sdk-ts` (a condition object is read by its `types`, `import` or `default` target, a `*` pattern by the files it matches) and fails when the type of an exported declaration refers to a declaration located in `libs/core/protocol`: a re-export, a signature, a member, a type argument, a base type or a constraint, found through the type checker. It fails when its selector matches nothing.
   - `all-ts-packages-eslint`: every directory under `libs` or `apps` that holds a `tsconfig.json` and a `package.json` has an `eslint.config.js`; it fails when its selector matches nothing.
   - `script-setup-holds-no-factory`: in the `<script setup>` of every shipped `.vue` file of `apps`, `libs` and `plugins`, no call of a `create*` function (DOM creators such as `createElement` aside) and no `async` function (`structure/ts/app-logic/check.mjs`). A factory and an async handler belong to the `model` segment.
   - `no-pass-through-factory`: a `create*` function of a shipped source under a `src` or `frontend` folder does not return an object that only copies fields of its parameters one by one; it has no other work (`structure/ts/app-logic/check.mjs`).
   - `documents-name-existing-paths`: every backticked path that starts with `libs/`, `apps/`, `plugins/`, `tools/` or `.agents/` in every Markdown file under `.agents/` and every `AGENTS.md` names a file or folder that is tracked; `*`, `<name>`, `(X)`, `{a,b}` and `...` stand for part of a path (`docs/paths-exist/check.mjs`).    - `typecheck-covers-sources`: no `exclude` entry of a tracked `tsconfig*.json` names a tracked file, as a path, a folder or a glob, read from the JSON syntax tree of the configuration.    - `no-component-below-ui`: over the modules dependency-cruiser reads (`readModuleGraph` in `structure/ts/dependency-graph/check.mjs`), no `.vue` file of a library, a window or a plugin frontend has `lib`, `api` or `model` as its nearest segment folder. It fails when its selector matches nothing.

## Structural checks

Every check below derives its subject from the repository (the manifests, `go.work`, the directories) and names no plugin, package or file. Each fails when its selector matches nothing, and each has a self-test in which a planted violation is reported, so a rule over nothing cannot pass.

- `plugins-isolation-capture`: one rule over the capture `plugins/(*)/`: a Go import or a package dependency of plugin X names plugin Y only when X equals Y. The imports of scripts are `dependency-graph`'s, and the Go import graph is checked by `the Go check `go/plugin-isolation-packages``, over the type-checked packages of every plugin module.
- `no-suppressions`: no `nolint`, `eslint-disable`, `eslint-enable`, `@ts-expect-error`, `@ts-ignore` or `@ts-nocheck` comment; no `exclusions`, `exclude-functions`, `exclude-rules`, `exclude-dirs`, `exclude-files` key in a golangci configuration; no source file named in an eslint `ignores` or `files` entry; no array of repository files, in a constant or inline, in a script of `tools/lint-layers` or `stylelint.config.mjs`. Generated code is detected by its `Code generated ... DO NOT EDIT` header and is not read. It reads comments with `typescript` and `@vue/compiler-sfc`, which `package.json` declares.
- `every-path-has-a-layer`: every Go module and npm package is under `libs`, `plugins`, `apps` or an auxiliary root (`tools`, `tests`, `docs`); no file is directly in a layer root; every plugin directory has a `manifest.json`.
- `workspace-lists-every-module`: `go.work` uses exactly the directories that hold a `go.mod`.
- `json-keys-camelcase`: every JSON key in a plugin manifest (including JSON schemas), API fixture and TypeScript JSON type is `camelCase`.
- Before a verifier that runs `golangci-lint` starts, the linter must be built with a Go no older than the `go` line of `go.work`.
